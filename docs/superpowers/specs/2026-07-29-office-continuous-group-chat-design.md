# Work APP 办公室持续群聊设计

## 目标

让办公室聊天呈现为自然、有限且不重复的现场互动：支持 2–4 人群聊，一名发起者留在当前地点，其他参与者主动走到其身边；聊天气泡为约两个头像宽的横向长条；API 可以分批续写对话，但台词播完后人物立即解散并恢复自主活动。

## 范围

本次只调整 Work APP 办公室内的聊天表现、对话续写和聊天集合方式。不改变项目管理、员工管理、A/B 调度模式、手动控制“我”的 10 秒规则，也不改动非聊天活动的文案和行为。

## 交互设计

### 气泡

- 气泡保持横向长条轮廓，目标宽度约为两个角色头像，即约 105–120px。
- 气泡不扩展为横跨屏幕的长横幅；靠近屏幕边缘时仍需保持在可视区域内。
- 每次只在当前说话人物上方显示一条气泡。
- 台词按顺序播放，不循环回到第一句。

### 集合与群聊

- 每次聊天必须有 2–4 名不同人物。
- 参与者列表中的第一人是发起者。发起者保留聊天开始时的当前位置，不前往固定聊天点。
- 其他 1–3 人分别走到发起者附近的不同位置，避免头像互相覆盖。
- 对话气泡在来访者完成移动后开始播放。
- 不再把所有参与者移动到画面底部的固定 `chat-1` 至 `chat-4` 集合点。
- 对话结束后取消聊天状态，人物可以在下一次调度中离开并执行工作、打印、休息、游戏等活动。

### API 持续对话

- API 每批返回 2–6 条新台词和布尔值 `shouldContinue`。
- 第一批请求包含人物设定、关系、项目、时间和参与者。
- 后续批次额外携带本轮近期聊天历史，要求承接已有话题，不复述旧台词。
- 播放接近当前批次末尾时预取下一批，避免明显空白等待。
- 当 API 返回 `shouldContinue: false` 时，当前批次播完即结束聊天。
- 单次聊天最多 3 批；即使 API 持续返回 `shouldContinue: true`，第三批播完也必须结束。
- API 请求失败时生成一批不重复的本地衔接台词；本地批次作为当前聊天的最后一批，播完后解散，不无限重试。

## 去重与轮换规则

- 将台词去除空白、常见标点和大小写差异后再比较。
- 新批次中与本轮历史完全相同的台词必须丢弃。
- 同一批次中的重复台词也必须丢弃。
- 新批次第一句不能由上一批最后一位说话者继续说；同一人物不能连续说两句。
- 过滤后不足两位不同人物发言时，该批次视为无效，转入本地兜底或结束聊天。
- 聊天历史只在当前会话内用于续写与去重；持久化缓存继续保持有界，避免无限增长。

## 状态与数据流

1. 场景计划选出 2–4 名聊天参与者，并把第一人标记为发起者。
2. 运行时读取发起者当前坐标，保留其位置，为其他参与者计算附近的可通行落点。
3. 来访者沿现有寻路系统移动到落点；全部到达后启动对话播放器。
4. 对话播放器请求首批 API 台词，逐句显示，并在接近末尾时预取下一批。
5. 播放器合并新批次前执行人物校验、连续说话校验和全文去重。
6. `shouldContinue: false`、第三批播完、有效台词不足或兜底批次播完时，结束当前聊天并触发重新调度。

## 错误处理

- 没有至少两名有效人物时不创建聊天。
- API 返回格式错误、超时或网络失败时，不回放已播台词。
- 首批 API 失败时使用符合人物和项目语境的本地台词；续批失败时使用一批新的本地收尾台词。
- 本地台词同样经过本轮历史去重，并保证至少两名不同人物参与。
- 单次续聊失败不弹出持续打扰用户的重复通知；办公室继续正常运行。

## 验收标准

- 气泡视觉宽度约两个头像，呈横向长条且不越出手机画面。
- 双人聊天中一人保持原地，另一人走过去；3–4 人群聊中发起者原地不动，其余人物使用不同落点靠近。
- 聊天从不只有一个人，也不会出现同一人物连续说两句。
- 同一句台词在一轮聊天中不会再次显示。
- 当前批次播放完不会从第一句重新循环。
- API 可以基于近期历史续写，最多连续 3 批。
- API 或本地台词表示结束后，人物退出聊天并恢复其他自主活动。
- A/B 模式、手动“我”控制、项目倒计时及其他活动保持原有行为。

## 测试策略

- 单元测试覆盖批次解析、`shouldContinue`、全文去重、说话人轮换、最多 3 批和结束条件。
- 调度测试覆盖 2、3、4 人聊天的原地发起者与不同来访落点。
- Hook 测试覆盖不循环、预取续批、失败收尾和对话结束后重新调度。
- UI/CSS 契约测试覆盖气泡宽度和横向形态。
- 浏览器验收覆盖两个现有手机视口，确认群聊移动、气泡展示和人物解散。
